# حسابات مدار والبيانات السحابية

هذا المجلد يحتوي إعداد قاعدة البيانات ودوال تسجيل الدخول باسم المستخدم وإدارة الحسابات. نشر الواجهة وحدها لا ينشئ قاعدة بيانات أو حسابات. تحتاج مشروع Supabase وتطبيق هذه الإعدادات أولاً.

## الإعداد في مشروع مجاني جديد

1. أنشئ مشروعاً في [Supabase](https://supabase.com/dashboard). انتظر اكتمال إنشاء قاعدة البيانات.
2. افتح SQL Editor وشغّل محتوى [ملف الترحيل](migrations/202610060001_cloud_accounts.sql) مرة واحدة **قبل إنشاء أول حساب في مدار**. البديل من Terminal داخل المشروع:

   ```bash
   npx supabase login
   npx supabase link --project-ref YOUR_PROJECT_REF
   npx supabase db push
   ```

   استخدم طريقة SQL Editor أو CLI. ملفات المشروع لا تحتوي مفاتيح الخادم؛ اختبر الإعداد على مشروعك بعد تطبيقه.

3. من Authentication > Providers فعّل Email، واترك تأكيد البريد مفعلاً. حساب مدار يتكون من اسم مستخدم، بريد لاستعادة الحساب، وكلمة مرور. اسم المستخدم يقبل `a-z` و`0-9` و`_` بطول 3–24، والاسم الظاهر يمكن كتابته بالعربية. اسم المستخدم محفوظ مرة واحدة عند التسجيل؛ تحديث بيانات Auth الوصفية لا يغيّره.
4. في Authentication > URL Configuration ضع رابط موقعك في Site URL، وأضف رابط الموقع وروابط التطوير إلى Redirect URLs. اقرأ تعليمات رابط استعادة كلمة المرور في دليل النشر الأساسي للمشروع.
5. اضبط أصول الواجهة المسموحة للدالة ثم انشرها:

   ```bash
   npx supabase secrets set ALLOWED_ORIGINS="http://localhost:5173,http://127.0.0.1:5173,https://YOUR_SITE.pages.dev"
   npx supabase functions deploy username-login --no-verify-jwt --use-api
   ```

   `--use-api` يجهز الدالة على الخادم، فلا يحتاج Docker على جهازك. `verify_jwt = false` مخصص لهذه الدالة لأن المستخدم لم يسجل الدخول بعد؛ التحقق من كلمة المرور يتم عبر Supabase Auth داخلها. `ALLOWED_ORIGINS` يقبل أصولاً كاملة دون مسارات أو `*`. عند غيابه تُسمح روابط التطوير فقط. أضف النطاق المخصص هنا إذا استعملته لاحقاً.

6. استخدم `VITE_SUPABASE_URL` ومفتاح `VITE_SUPABASE_PUBLISHABLE_KEY` العام في إعداد الواجهة. ملفات الدالة تقرأ مفاتيح Supabase المحقونة على الخادم تلقائياً، وتدعم مفاتيح المشاريع الحديثة والقديمة. **لا تضع مفتاح `service_role` أو `sb_secret_` في متغير يبدأ بـ `VITE_`، أو في الكود، أو في ملف ZIP.**
7. قبل الاعتماد على الموقع، أنشئ حسابين مختلفين وتحقق من أن كل حساب يرى بياناته فقط، وجرّب تأكيد البريد واستعادة كلمة المرور وتسجيل الدخول من جهاز ثانٍ. اختبارات المشروع المحلية لا تستبدل هذه التجربة على مشروعك.

## تفعيل لوحة الأدمن

طبّق [الترحيل الثاني](migrations/202610070001_account_administration.sql) بعد الترحيل الأساسي، ثم اتبع [دليل نشر الإدارة من لوحة Supabase](dashboard-admin-deploy.md). ملف [promote-owner.sql](promote-owner.sql) يمنح الإدارة للحساب الموجود `mustafaasad` من SQL Editor فقط؛ لا يُنفّذ تلقائياً ضمن التسجيل أو الترحيل. انشر `account-admin` بعد الترحيل، واترك مفاتيح الخادم في بيئة Supabase.

الأدوار وسجل العمليات في مخطط `private`، وإجراءات الإدارة RPCs مخصصة للخادم. قاعدة البيانات تمنع الحساب الموقوف من قراءة المساحة أو حفظها حتى لو كانت جلسة JWT لم تنتهِ. تشرح [وثيقة إدارة الحسابات](../docs/account-administration.md) حالات الفشل الجزئي وحماية المدراء والحذف النهائي.

## ما الذي يحمي البيانات؟

- `account_profiles`: الاسم واسم المستخدم فقط، دون بريد. المستخدم المسجل يقرأ صفه فقط. لا يسمح باستعراض أسماء المستخدمين أو البحث عن بريد حساب من المتصفح.
- `user_workspaces`: نسخة JSON خاصة بكل مستخدم، معها رقم إصدار `revision`. القراءة تخضع لـ RLS؛ الكتابة المباشرة إلى الجدول ممنوعة.
- `save_workspace(p_payload, p_expected_revision, p_user_id)`: المسار الوحيد للحفظ من الواجهة. يجب أن يطابق المستخدم الملتقط في الطلب هوية JWT، مما يمنع طلباً قديمًا من الكتابة إلى حساب آخر بعد تبديل الحساب. إصدار `0` ينشئ الصف وإصداره `1`؛ كل حفظ يزيد الإصدار. طلب قديم يرجع `40001 / workspace_conflict` حتى يقرأ العميل النسخة الحديثة ويعالج التعارض.
- الدالة ترفض بنية JSON غير صحيحة ونسخاً تتجاوز 5 MiB. التحقق التفصيلي من حقول المهام والمهارات يتم أيضاً في الواجهة؛ هذا ليس بديلاً عن صلاحيات المستخدم.
- `username-login`: يحوّل اسم المستخدم إلى حساب Auth على الخادم، ثم يتحقق من كلمة المرور. النجاح يعيد رمزي الجلسة فقط؛ الأخطاء لا تعيد بريداً أو تفاصيل SDK. البريد المخزن في حسابك يبقى لدى Supabase Auth.
- محدد المحاولات موجود في مخطط `private`، ولا يمكن للمتصفح استدعاؤه. يخزن HMAC لأسماء المستخدمين وعناوين IP، دون تخزين القيم الأصلية أو كلمات المرور. الحد 30 محاولة لكل اسم مستخدم و100 لكل مجموعة IP خلال 15 دقيقة. الاسم له حد مستقل لأن ترويسات IP تعتمد على وكيل الاستضافة ويمكن التلاعب بها؛ لا تعتمد الحماية على IP وحده. بعد انتهاء النافذة يتجدد الحد، ويُحذف السجل القديم تدريجياً أثناء الطلبات. حدود Supabase Auth تبقى سارية كذلك.

حد الاسم قد يوقف تسجيل الدخول بهذا الاسم مؤقتاً إذا استهدفه شخص بمحاولات كثيرة. يستطيع المالك الدخول بالبريد، أو الانتظار 15 دقيقة. هذه نسخة شخصية؛ عند فتح التسجيل للجمهور يمكن إضافة CAPTCHA، وضبط حدود Auth وإرسال البريد عبر SMTP. CORS يضبط المتصفح، ولا يعد وسيلة مصادقة للطلبات المباشرة.

حذف المستخدم من لوحة Authentication يحذف صف الملف وبياناته السحابية المرتبطة. لا يحذف تلقائياً نسخة احتياطية سبق تنزيلها أو بيانات جهاز محلي.

## التحقق المحلي

اختبارات دالة تسجيل الدخول لا تحتاج مشروعاً سحابياً:

```bash
node --experimental-strip-types --test supabase/tests/login-helpers.test.ts
```

لاختبار SQL فعلياً على PostgreSQL 17 تحتاج Docker وBash و`rg`:

```bash
bash supabase/tests/run-db-tests.sh
```

الاختبار ينشئ حاوية مؤقتة، دون منافذ عامة أو مجلدات من الجهاز، ويحذفها عند الانتهاء. يفحص صلاحيات القراءة والكتابة، عزل المستخدمين، حارس تبديل الحساب، صحة JSON وحجمه، حفظين متزامنين، محدد المحاولات، وحذف البيانات عند حذف الحساب. يستخدم جدول Auth صغيراً لاختبار حدود قاعدة البيانات؛ لا يشغّل Supabase Auth أو إرسال البريد.

يمكن تدقيق TypeScript للدالة عبر Deno:

```bash
deno check supabase/functions/username-login/index.ts
```
