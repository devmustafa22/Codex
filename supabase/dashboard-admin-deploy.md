# تفعيل الإدارة من لوحة Supabase

هذه خطوات لتحديث مشروع مدار الحالي، ولا تحتاج تنزيل ZIP أو كتابة أوامر على جهازك. الحساب الذي سيصبح الأدمن هو `mustafaasad`، بنفس كلمة مروره الحالية. الملفات لا تمنحه صلاحية إلا بعد أن تنفّذ خطوة المنح صراحةً في قاعدة بياناتك.

إذا حسابات مدار والحفظ السحابي تعمل لديك، لا تُعد ترحيل الحسابات القديم `202610060001_cloud_accounts.sql`. تحتاج الترحيل الجديد فقط.

## 1. تطبيق ترحيل الإدارة

1. افتح [مستودع مدار](https://github.com/devmustafa22/Codex) في تبويب ثانٍ.
2. افتح ملف `supabase/migrations/202610070001_account_administration.sql`، ثم اضغط **Raw** لعرض النص الكامل ونسخه. تجنب نسخ معاينة مقصوصة من صفحة GitHub.
3. افتح مشروعك في [Supabase](https://supabase.com/dashboard)، ثم **SQL Editor → New query**. تأكد أن الدور المختار هو `postgres`.
4. الصق النص الكامل واضغط **Run**. ظهور **Success. No rows returned** يعني اكتمال أوامر الترحيل. إذا ظهر خطأ، توقف عنده؛ لا تحاول تعويضه بتعديل صلاحيات عشوائية.

الترحيل يضيف حالة الحساب وحدود وصول الحساب الموقوف وقائمة الإدارة والسجل. لا يغيّر بيانات المهام الموجودة، ولا يجعل أول حساب أو أي اسم مستخدم أدمن تلقائياً.

## 2. منح حسابك صلاحية الإدارة

1. من نفس المستودع افتح [supabase/promote-owner.sql](https://github.com/devmustafa22/Codex/blob/main/supabase/promote-owner.sql)، واضغط **Raw** ثم انسخ النص كله.
2. افتح **New query** في SQL Editor بالدور `postgres`، والصق النص واضغط **Run**.
3. يجب أن تظهر نتيجة فيها اسم المستخدم `mustafaasad` وحالة `active` وصلاحية `admin`.

هذا الملف يحلّ اسم المستخدم إلى الحساب الموجود بالضبط، ولا ينشئ حساباً أو يغيّر كلمة مروره. إذا لم يوجد الاسم، يعطي خطأ واضحاً ويتراجع دون منح أي حساب آخر. يجوز إعادة تشغيله لنفس الحساب دون تكرار صف الإدارة.

لا تنسخ هذا الملف إلى محرر دوال Edge Functions. هو أمر SQL خاص بمالك المشروع، ولا ينبغي أن تستدعيه الواجهة.

## 3. إنشاء دالة الإدارة

1. من قائمة Supabase افتح **Edge Functions → Deploy a new function → Via Editor**. قد تظهر أسماء مثل **Create function** أو **Editor** حسب نسخة لوحة التحكم.
2. سمِّ الدالة `account-admin` بالضبط.
3. افتح ملف [supabase/dashboard-account-admin.ts](https://github.com/devmustafa22/Codex/blob/main/supabase/dashboard-account-admin.ts) من GitHub، واضغط **Raw** وانسخ النص كله.
4. استبدل به الكود الافتراضي في `index.ts` داخل محرر Supabase. هذا ملف واحد مكتمل ولا يحتاج ملفات إضافية.
5. اضغط **Deploy function** وانتظر نجاح النشر.
6. افتح إعدادات الدالة وعطّل **Verify JWT with legacy secret** أو **Enforce JWT verification**، ثم احفظ التغيير إن كان زر الحفظ متاحاً.

تعطيل فحص JWT القديم في البوابة لا يجعل الإدارة مفتوحة. دالة `account-admin` تطلب رمز جلسة المستخدم وتتحقق منه عبر `auth.getUser`، ثم تتحقق قاعدة البيانات من أن الحساب أدمن فعّال في كل عملية. بيانات المستخدم الوصفية أو كلمة `admin` المرسلة من المتصفح لا تمنح أي صلاحية.

الدالة تقرأ مفاتيح الخادم التي تحقنها Supabase تلقائياً. لا تحتاج إضافة كلمة مرورك أو نسخ `service_role` أو `sb_secret_` إلى الكود أو Cloudflare أو GitHub.

## 4. التحقق من عنوان الموقع

سبق ضبط `ALLOWED_ORIGINS` لدالة `username-login` في مشروعك. الدالة الجديدة تستخدم نفس المتغير الموجود في **Edge Functions → Secrets**، لذلك لا تنشئ نسخة ثانية باسمه.

للموقع الحالي، يجب أن تشمل القيمة:

```text
http://localhost:5173,http://127.0.0.1:5173,https://codex.mustafaasad08.workers.dev
```

إذا كان هذا هو النص المحفوظ، لا تحتاج تغييره. الأصل هو البروتوكول والنطاق والمنفذ فقط؛ لا تضف مسارات أو `/` في النهاية أو نجمة `*`. عند نقل الموقع إلى نطاق جديد أضفه مع الإبقاء على الأصول المطلوبة.

## 5. فتح الإدارة وتجربتها

بعد نشر الواجهة المحدّثة من GitHub واكتمال بناء Cloudflare، افتح [مدار](https://codex.mustafaasad08.workers.dev)، وحدّث الصفحة. سجّل بحساب `mustafaasad` أو سجّل الخروج والدخول به إذا بقيت صلاحيات الجلسة المعروضة قديمة. يظهر قسم الإدارة بعد نجاح قراءة الصلاحية من الخادم.

اختبر العرض، ثم التوقيف وإعادة التفعيل على حساب تجربة عادي. جرّب الدخول والحفظ بالحساب الموقوف من متصفح آخر أيضاً. اختبر الحذف فقط على حساب تجربة لا يحمل بيانات مهمة؛ يطلب التطبيق كتابة اسم المستخدم قبل الحذف.

إذا ظهرت رسالة أن نتيجة الحذف غير معروفة، توقف عن تكراره وراجع وجود المستخدم في **Authentication → Users** وسجل الدالة. الحذف المعلّق يحتاج مراجعة مالك المشروع، ولا يتحول إلى حساب فعّال تلقائياً بعد انتظار مدة.

تفاصيل السلوك وحدوده موجودة في [دليل إدارة الحسابات](../docs/account-administration.md). لا تعتبر رفع الكود أو نجاح نشر الدالة وحدهما إثباتاً لعمل التوقيف؛ التجربة من الحسابين تؤكد الإعداد على مشروعك الفعلي.

## إذا لم يظهر قسم الإدارة

- تحقق من نجاح الترحيل الجديد وظهور `admin` في نتيجة `promote-owner.sql`.
- تحقق من أن اسم الحساب الحالي `mustafaasad` وأن بناء Cloudflare يستخدم آخر تحديث من فرع `main`.
- تحقق من وجود دالة اسمها `account-admin` ومن إعداد Verify JWT وقيمة `ALLOWED_ORIGINS`.
- راجع الخطأ الظاهر في مدار. إذا ظهر خطأ عام بالخادم، افتح سجلات الدالة في Supabase؛ لا تنشر رموز الجلسة أو مفاتيح الخادم عند إرسال صورة الخطأ.

## بديل للمطور عبر CLI

بعد ربط CLI بنفس المشروع وتطبيق الترحيلات، شغّل ملف المنح داخل SQL Editor كما سبق، ثم انشر الدالة:

```bash
npx supabase functions deploy account-admin --no-verify-jwt --use-api
```

إذا طبّقت SQL من المحرر، لا تستخدم `db push` لنفس الترحيل لاحقاً قبل تسوية سجل الهجرة. لا يحتاج هذا الدليل تغيير دالة `username-login` الموجودة.
